# v0 research update — provider, event and projection boundaries

Status: **DRAFT DESIGN UPDATE / NOT IMPLEMENTED**  
Updated: 2026-09-09

## Why this update exists

The 2026-09-06 detailed design was written before two newer HISTOS research targets were added and before the cross-tool Agent Skills format was checked as a projection path. The core authority/provenance design remains sound; the implementation strategy should change so HISTOS does not rebuild components that can be evaluated behind stable contracts.

## New decisions

### D11 — Evidence Event precedes Memory Candidate

Harness events are normalized into a typed evidence/event envelope before any model decides what should be remembered. User correction, verifier result, tool failure/retry, successful deterministic check and repeated operation become routable signals. Friction decides **what is worth examining**, not what is true.

See [`../../EVIDENCE_EVENT_CONTRACT.md`](../../EVIDENCE_EVENT_CONTRACT.md).

### D12 — Memory and distillation are provider interfaces

HISTOS Kernel owns scope, source/evidence identity, anti-self-corroboration requirements, Context compilation and provider admission. A Memory Provider may store/recall durable memories; a Distillation Provider may turn eligible evidence events into candidates. Neither may mint current truth or authorization.

`distill-kura` is the first explicit experimental Memory+Distillation provider candidate because its source exposes deterministic quote verification, echo suppression and read-only MCP enforcement. This is a research path, not an adoption decision.

### D13 — Grounding receipts are first-class

A provider-generated memory candidate should return enough deterministic grounding information to prove which raw evidence survived its gate and which claims remain judgement/inference. Provider confidence text is not sufficient. HISTOS can reject or quarantine candidates that cannot descend to acceptable source/evidence references.

### D14 — Recall utility is separate from epistemic support

TeamAI currently records recall/use feedback and uses friction to select sessions worth documenting. HISTOS may learn from usage, successful downstream verification and human correction, but `recalled_count`, popularity or repeated model mentions must never increment proof/support by themselves.

### D15 — Procedural projection uses standards before bespoke sync

A supported, reviewed procedure can be rendered as a portable Agent Skill package when the target harness supports that format. Harness-specific files remain thin adapters for installation/location/UI metadata and permissions. Current project state, secrets and Mission authority do not belong inside generated Skills.

See [`../../AGENT_SKILLS_RESEARCH_TARGET.md`](../../AGENT_SKILLS_RESEARCH_TARGET.md) and [`../../PROVIDER_PROJECTION_ARCHITECTURE.md`](../../PROVIDER_PROJECTION_ARCHITECTURE.md).

## Revised near-term order

```text
H0a  freeze Source/Snapshot/Artifact + Evidence Event + Provider contracts
H0b  freeze benchmark and model-visible budget measurement
H1   exact artifact externalization / scoped read / recovery
H2   lexical + structural Context Compiler and selection receipts
H3   Codex + OpenCode assisted-MCP daily use
     + experimental Kura Memory Provider read path
     + synthetic/manual Agent Skill projection proof
H4   provider-neutral Memory Candidate / revision acceptance
     + evidence-gated Kura distillation experiment
H5   compiled understanding + bounded/coalesced consolidation
H6   EPHEMERA role-scoped integration + existing Console read models
H7+  optional graph/vector/document providers, automation candidates,
     retrieval-policy learning only after measured value
```

The Kura read experiment does not need to wait for H4 because it can be treated as a read-only context source. Kura-backed writes/distillation do wait for the Memory Candidate/grounding acceptance contract.

A Skill projection proof may use a synthetic reviewed procedure before H4 to test portability, but automatic experience-to-Skill promotion remains a later gated capability.

## Bootstrap strategy

Do not inject a full resident memory map or full generated knowledge base into every session. Prefer a small stable pointer/skill/rule that tells the harness when and how to ask HISTOS, followed by on-demand retrieval. Upstream Kura itself documents inconsistent MCP initialize-instruction behavior across clients, and TeamAI moved away from SessionStart auto-recall toward active retrieval. Treat host bootstrap behavior as an integration fact to measure, not a protocol guarantee.

## Research gates added

Before selecting a native memory backend or Kura as default:

- compare Kura recall against lexical/file-native baselines under fixed budgets;
- measure exact evidence descent and abstention/false recall;
- verify read/write capability isolation mechanically;
- replay duplicate/echo/retrieved-memory contamination cases;
- measure background distillation cost and failure visibility.

Before adopting friction-triggered capture:

- replay real sessions with independently identified reusable outcomes;
- measure trigger precision/recall and cost avoided;
- include positive smooth-session discoveries so friction is not the only route.

Before adopting Agent Skills projection:

- render one procedure from one canonical revision;
- validate against the open Agent Skills spec;
- install it into both a supported Codex setup and OpenCode without changing the procedural body;
- prove uninstall/update ownership, version drift and permissions;
- measure startup discovery overhead and activation precision.
